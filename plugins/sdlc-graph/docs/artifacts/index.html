sdlc-graph v1.0.3

What actually happens when you run it

One guarded graph drives a feature from an idea to a merged PR. The orchestrator evaluates every guard and owns the run state; a milestone agent runs each milestone's six-node loop and returns one verified bundle. Walk the green path below — every node shows what it actually does, what it writes, and where it can go next.

19nodes — 17 on the green path, 2 only on failure
42guarded edges. Zero matches is BLOCKED, never a guess
10bounded retry cycles, each with its own counter
6human stops — 14 of 20 nodes never ask
1Workflow script in the whole graph, at GATE_A
14return-gate checks, R0–R13, before any hop is recorded

Three rules the rest follows from

  • The orchestrator evaluates every guard. The milestone agent evaluates none. A milestone agent is handed a fixed itinerary computed before the spawn, and branches inside it only on facts — a red suite goes to DEBUG. It never decides which edge the run takes.
  • Verify before you record. Nothing enters history[] until the returned bundle passes R0–R13, and seven of those checks read the world (git, the test suite, the filesystem) rather than the bundle.
  • A gate that could not run is written down, not skipped silently. An absent tool appends a skipped_gates[] entry, the node may never be recorded as passed, and the run proceeds. The ledger is the cost; the halt would be the bug.

What changed, and why

before — three different tails

A/B  GATE_B → PR → CI → MERGE → CLOSE_OUT → QA → VERDICT → DONE
C    GATE_B → PR → CI → MERGE → BRANCH → … → CLOSE_OUT → QA → VERDICT
  • Everything after MERGE committed past the only review gate: plan-file updates, CLAUDE.md changes, the QA plan and report — and per VERDICT, every confirmed finding converted into a committed test.
  • A BLOCK verdict meant broken work was already in main and had to be fixed forward.
  • C bought independent landing with a PR, a CI run and a merge per milestone — and its "parallel worktrees" were a note in a script nothing dispatched.

after — one tail, three loops

A/B  GATE_B → ⎫
C    GATE_B → CONSOLIDATE → GATE_B → ⎬ CLOSE_OUT → PR → CI → QA → VERDICT → MERGE → DONE
  • The diff a human approves carries its own QA verdict, plan updates, CLAUDE.md changes and regression tests.
  • A BLOCK never reaches main — it re-enters at BRANCH on the one open branch, and pushes to the already-open PR.
  • C is genuinely parallel: a worktree per milestone, independent ones concurrent, merged locally into one integration branch. One PR, one QA pass, one merge — under every strategy.
  • The concurrency is real now, not a note in a script nothing dispatched. Each milestone's loop runs in its own milestone agent, and under C they are spawned together.
Why CI still comes before QA. CI's input is milestones[cursor].pr — it needs an open PR to watch, so it cannot precede PR. And QA-ing a branch that fails CI wastes the most expensive node in the graph.

CONSOLIDATE — the node that lets C rejoin the tail

StepWhat it doesWhy it is not optional
1Create <task-id>/integration off mainThe one branch everything downstream acts on — PR, CI, QA, MERGE.
2Merge every milestone branch, parents before childrenA dependent milestone was branched off its parent. Out of order, the parent's commits replay as conflicts against a base that does not contain them.
3Run the integrated unit + integration suiteN independently-green branches are not a green whole. This is the only place a semantic conflict can surface before CI.
4git worktree remove each oneWorktrees hold checked-out branches; leaving them makes later branch deletion fail. Failure here is a skipped_gates[] entry, never a block.

Two failure modes, kept deliberately apart. A textual conflict — two milestones edited the same lines — goes to BLOCKED with the paths named, because git cannot resolve it and the graph must not guess. A semantic conflict — git merged cleanly and the suite went red — goes to DEBUG, bounded at 3, because that is a real defect with a root cause.

Every node, and what it owns

All 19 contracts, from the same dataset the Run stepper and the Graph panel read — so there is no second copy to drift. Every node declares the same shape: action · emits · exit guards · max attempts · requires. A missing requires tool writes a skipped-gate entry and the node may never be recorded as passed.

How the work is handed out, and how it is checked coming back

The graph delegates two ways: one Workflow script, for the one node whose work is wide rather than deep, and one milestone agent per milestone, which keeps whole diffs and test output out of the orchestrator's context. Both are only safe because of what happens on the return.

Where the Workflow is, and what it does

Exactly one node dispatches a Workflow: GATE_A

Everything else in this graph is an orchestrator turn or an agent. GATE_A is the exception because it is the one node whose work is wide — every changed file needs four review passes, and a single agent told to read 40 files properly cannot. The script exists to fan that out without losing coverage.

Workflow({
  scriptPath: "${CLAUDE_PLUGIN_ROOT}/skills/sdlc-graph/workflows/gate-a.workflow.js",
  args: {
    files:         ["src/auth/auth.service.ts", "src/auth/auth.controller.ts"],  // array, repo-relative
    milestone:     2,                                        // labelling only
    tools:         { reviewer: true, simplifier: false, security: true },  // the preflight result
    filesPerGroup: 12                                        // quality limit, not a cap
  }
})

What it does, in order

  1. Validates files. A stringified list does not throw — strings are iterable, so it would silently walk characters and review nothing. The script refuses it, along with absolute paths and any .. segment.
  2. Groups by directory — a "logical module", so the reviewer sees the service, its controller and its tests as one thing. A module larger than filesPerGroup is split, never truncated.
  3. Runs four steps per file, strictly in order: Code Review → Simplification → Security Review → Final Review, applying each step's findings before the next. Groups run concurrently; the steps within a file do not.
  4. Re-verifies unit + integration — steps 2 and 3 edited code that was green on entry.
  5. Returns the whole result object, which the milestone agent puts in evidence.gate_a untouched. It chooses no edge.

What comes back

{ clean, rerun_recommended, rerun_reasons,
  findings, skipped_steps, tools_asserted,
  applied, uncovered,
  groups_completed, groups_total,
  files_reviewed, files_supplied, groups }

The graph routes on rerun_recommended, never on clean. clean also goes false when a reviewer is merely absent — routing on it meant "reviewer not installed + suite green" matched zero guards, and a real run halted on it twice.

It degrades context, never coverage

Group count is derived from filesPerGroup and is deliberately uncapped — pipeline() queues, so 85 groups all complete at roughly 16 at a time. Concurrency has never limited what gets reviewed.

The one hard limit is the Workflow runtime's 1,000 agents per script lifetime. Past roughly 2,850 files the script widens groups to fit rather than dropping files, so uncovered should always be empty — a non-empty one is a bug, not an expected outcome. This is also why the milestone loop is an Agent and not a script: a milestone agent script driving three milestones would pull three fan-outs into one 1,000-agent budget and exhaust it silently, mid-run, on the third.

When there is no Workflow tool

The tool is not guaranteed inside a subagent session, and a real run found that out: the milestone agent there ran Gate A's four steps by dispatching the reviewers directly — same order, same files, same fixes applied, no script. So the milestone agent says how it ran the gate, and the return gate reads it accordingly.

gate_a.dispatchMeansrun_id / groups_*groups_completed == 0
"workflow"the script ranrequired; the runId must appear in the milestone agent's journaldispatch failure — counts GATE_A-dispatch
"direct"no Workflow tool here; four steps ran as agentsnull — inventing either is fabricationmeaningless; there were never any groups. Charges nothing

direct is not a skipped gate. The gate ran; only its dispatcher differed. Ledgering it would record that Gate A did not happen — false — and would then bar the node from being recorded as passed, penalising a run for the shape of its own runtime. What direct costs is the script's coverage arithmetic, so files_supplied, uncovered_count and applied ⊆ git diff carry that weight instead.

The milestone agent

One agent, one milestone, six nodes, one return

The orchestrator spawns one milestone agent per milestone and hands it a fixed itinerary. Between the spawn and the return it runs the whole loop — BRANCH → IMPLEMENT → TEST → GATE_A → [E2E] → GATE_B — plus any DEBUG round-trips those nodes route to.

context.has_uiItinerary, fixed at spawn time
trueBRANCH → IMPLEMENT → TEST → GATE_A → E2E → GATE_B, then return
falseBRANCH → IMPLEMENT → TEST → GATE_A → GATE_B, then return
nullBRANCH → IMPLEMENT → TEST → GATE_A, then return immediately — an unresolved has_ui is a halt, not a default branch

The milestone agent's last transition is into GATE_B. Its exits (15 / 16 / 17) read run-level state the milestone agent was never given, so those belong to the orchestrator. It also means the trace alone cannot tell a Gate B that ran from one merely arrived at, which is what R3 checks against the evidence blocks.

Runtime telemetry — three tiers

A milestone agent used to be invisible from spawn to return: six nodes over a long stretch, and the orchestrator learned nothing until an 8 KB bundle arrived. Each milestone agent now appends to its own append-only journal at docs/graph-runs/<run-id>/journals/milestone-<milestone>.jsonl as it leaves each node. One file per milestone, one writer per file — under strategy C, N milestones sharing a file would mean N concurrent read-modify-write cycles with no lock.

1 · Headline — pushed2 · Record — pulled3 · Interrogation — asked
Size~120 tokens1–2k tokensas large as the answer needs
WhereJSONL headline, streamed by MonitorJSONL detail, on diskSendMessage to milestones[].agent_id
Triggerevery node exit, alwaysthe orchestrator decides — two moments are mandatorya question the record does not answer
Carriesnode, milestone, one-line summary, counts, shas, elapsedwhat was built and why, decisions, interfaces added, gotchas, what the next milestone must knowanything the milestone agent still holds — the full diff, the failing assertion, why a fix was chosen

Telemetry, not evidence. Nothing routes on the journal, with exactly one exception — and that one runs the other way round. R13 does not use the journal to prove something happened; it uses it to catch the bundle omitting something. A milestone agent would have to lie twice, in opposite directions and at different times, to defeat it.

Tier 3 is questions only, never instructions. A returned milestone agent keeps its context, so the orchestrator can ask why did the auth interface change? without that context ever living in its own window. Telling a milestone agent to "just also fix that" would re-drive a milestone with no branch discipline, no preflight and no return gate. And an answer is prose from the agent the gate exists to check: it informs, it never satisfies an R-check.

The return gate — R0 to R13

When a milestone agent returns, nothing it claims is recorded until it is checked. The whole gate runs before any write, cheap checks first, on a hard budget of 20 lines of output — every command redirects to a file and the orchestrator reads an exit code, a count or a tail line. A check that cannot fit that budget is the wrong check, because re-importing the context is the thing delegation exists to avoid.

The floor: at least one world-sourced check per node

The bundle is agent-asserted throughout. These are not, and they are what the design rests on.

What every file does, and what the run remembers

Most of this plugin is instructions a model reads; some is JavaScript that actually executes; one is an agent spawned in its own context that runs the entire milestone loop. Nothing about a directory listing tells you which is which.

The one distinction that matters

KindWhat it isWhat happens to it
markdownInstructions written for the model Read into context and followed. Nothing "runs". If the model does not read the file, nothing in it happens.
javascriptReal code Actually executed by the Workflow tool. Deterministic — it does the same thing every time, whatever the model thinks.
agentA prompt for a separate model instance Spawned with its own fresh context. It cannot see this conversation, and returns only its result.
configManifest Read by Claude Code at install time. Never during a run.

The practical consequence. A rule in a Markdown file is only in force if that file was read. That is why SKILL.md opens by ordering the model to load nodes.md, edges.md and state.md before the first transition — and why node procedures load lazily, only when their node runs. A rule in qa-engineer-node.md does nothing until the QA node executes. The .js files are the opposite: they run exactly as written regardless of what any Markdown says, which is precisely why the fan-out lives in code — a review pipeline that "usually" runs four steps is not a gate.

The state file is the whole point

A run is one directory, and it is gitignored — INTAKE adds docs/graph-runs/ to the project's .gitignore before creating it. A run is working memory; the committed plan file is the record that survives.

docs/graph-runs/<run-id>/
├── state.json                       // written on EVERY transition, before the next node starts
├── journals/milestone-<id>.jsonl    // one per milestone agent — that agent is its only writer
└── history/                         // only with --trace
    └── 0007_m2_GATE_A-to-E2E_20260808T094402Z.json

A crash between two nodes leaves a file that says exactly where the run was.

  "skipped_gates": [ { "node": "GATE_A.step2",
                       "reason": "code-simplifier not installed" } ],
  "history":    [ { "from": "TEST", "to": "GATE_A",
                    "guard": "unit and integration green",
                    "observation": "green on the 2nd attempt; the 1st failed on a fixture" } ]
}

Every transition carries an observation — one line on what actually happened in the node just left, not what the guard says. It is the only verified per-node record, written after the return gate passes.

skipped_gates[] is the field the design turns on. Two source skills said never report a gate as passed when its tool was absent — but in prose nothing records the absence, so the rule is unenforceable. Here it is mechanical: a missing tool appends an entry, the node cannot be marked passed, close-out copies it into the plan, and DONE leads with it. Entries are append-only — installing the tool later does not retroactively pass the gate.

Provisional is not recorded. milestones[].progress.at_node says where a milestone agent claims to be. It drives the viewer and the orchestrator's supervision; it never advances the run and is cleared on replay. Only history[] is the record, and it is written after the gate.

--trace keeps every state, not just the last one. state.json is overwritten at every hop, so on an ordinary run the counters as they climbed, the progress block and the ledger as it grew are simply gone. With --trace the plugin's own PostToolUse hook copies each write into history/, numbered and named after the transition that produced it — so ls reads as the run's story. Off by default, and telemetry rather than evidence: nothing routes on it, and the hook has no non-zero exit path, because a lost snapshot must never be an interrupted run.

Resume reads this file, then re-derives progress from the world — was the branch created? are tests green? has the PR merged? The filesystem and git are the truth; the file only says where to look. Counters are never rewound, because rewinding hands a stuck loop an unlimited budget.

Ten cycles, ten bounds

This is what the graph adds that the prose skills could not state. Each of these cycles existed already — "fix it and re-run", "reopen for S1/S2", "watch the build and fix it". None of them named a limit, and an agent following prose will re-run a failing gate until something else stops it.

CycleBoundOn exhaustion
TEST ↔ DEBUG3BLOCKED, surfacing the failure and every fix tried
E2E ↔ DEBUG3BLOCKED
GATE_A ↔ DEBUG2BLOCKED — Gate A's own simplify and security edits change code that was green on entry, so a break there needs somewhere to go
GATE_A ↻ GATE_A1proceeds — the one cycle that does not block. For a genuine bug, security issue or regression only; never a style nit
GATE_A dispatch retry1BLOCKED — and it has its own counter. A workflow that died having run zero agents reviewed nothing, so it must not spend the findings budget: a real run had a crashed dispatch consume the re-run allowance, silently downgrading a security re-review
GATE_B ↔ DEBUG2BLOCKED
CONSOLIDATE ↔ DEBUG3BLOCKED, naming the two milestones whose merge broke it. A textual conflict never comes here — git cannot resolve it and the graph must not guess, so that blocks directly
CI ↔ DEBUG15mbudget, plus a two-same-error guard, then STILL-RED or BLOCKED
VERDICT → BRANCH2BLOCKED — a human decision
PLAN → PLAN∞unbounded on purpose — a conversation, not a retry. Bounding it would cut off the cheapest correction in the run

Counters are keyed per milestone (attempts["TEST:2"]) and are never reset, only keyed — so milestone 3 starts fresh while a stuck loop on milestone 2 stays stuck. A resumed run inherits the counter it left behind.

Four states a run can end in

RUNNINGMid-flight. Written on every transition, before the next node starts.
BLOCKEDSomething failed: a bound exhausted, or no guard could be satisfied. Records the node, every guard tested, and what was tried. Resumable.
HANDOFFA deliberate stop with nothing wrong. Only strategy D reaches it. Kept separate from BLOCKED so nobody hunts for a failure that never happened.
DONEReached the end — not necessarily clean. Check the skipped-gate ledger before believing it.

Six stops, and nowhere else

StopTypeWhat it needs

The list is derived from the human field on each node contract rather than maintained separately — so the two cannot drift apart. run_mode adds cadence on top: checkpoint stops after every milestone's GATE_B, on-exception whenever a gate is skipped, a bound is exhausted, or a milestone bundle is rejected.

How this graph is tested

Two methods, and they answer different questions. One reads the specification and asks whether it contradicts itself. The other runs the graph with real agents and asks whether it behaves. Neither substitutes for the other.

Every check exists because a real run hit the defect it catches. None is hypothetical, and several were added the same day the bug they describe was found — including three in checks that had been printing ok while testing nothing.

The rule this whole directory turns on: a change is not finished until it adds the eval that would have caught its absence — and that eval is not finished until a deliberately broken input makes it fail. A check that cannot fail is not evidence.

Method 1 — deterministic no agents

Reads the spec files and the fixtures. No model, no network, no dependencies. Runs in seconds.

Method 2 — executing real agents

The deterministic suites cannot catch an orchestrator that reads the contract correctly and then behaves wrong: spawns before arming its monitor, writes history[] from a bundle it never gated, or answers a dead milestone agent by waiting longer. Those are behaviours, and a behaviour has to be run to be observed.

2a · evals/runs/ — scripted counterpart

subagent = ROOT→ mock_milestone.py→ artifacts→ assertions

A subagent plays the orchestrator against mock_milestone.py — a milestone agent with the model taken out, which emits exactly the journal lines the scenario dictates and returns exactly the bundle it dictates, including a dishonest one. Ten scenarios, each with a control that must break it; --self-test runs only the controls and needs no agent at all.

This tier keeps its place for the two things a real agent cannot be relied on to do: lie in one exact way (a bundle that hides precisely one retry) and die mid-node.

2b · evals/real/ — both sides real

subagent = ROOT→ subagent = MILESTONE→ real repo, real code, real tests
deterministic: start · path · end+ judge = top-level orchestrator→ verdict

A scripted milestone agent satisfies the journal contract by construction: perfect lines, correct seq, appended before it returns. But almost every demand in that contract is on the milestone agent — append as you leave each node rather than reconstructing on the way out, write a detail useful to a reader with none of your context, never touch a sibling's file. None of it can be observed against a fixture that cannot fail it, and the likeliest real failure — a thin useless detail, or a journal written from memory at the end — is invisible there.

So here both sides are real, and the target is a genuine git repository with test scripts that actually run. Attribution does not need a scripted side: the artifacts are already separated by author. Journal shape is the milestone agent's. State-file writes are the root's.

What is never done: asking the actor under test how it did. That is a self-report from the thing being checked — the exact failure the return gate exists to prevent, rebuilt one level up inside the test harness.

The pattern is stable: the deterministic suites find drift and dead checks; the executing ones find contradictions that only appear when someone has to obey both rules at once.
